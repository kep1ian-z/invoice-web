# PRD 작성 메타프롬프트 — 견적서 웹 조회 & PDF 다운로드 서비스

이 문서는 "Notion에 입력한 견적서를 클라이언트가 웹에서 확인하고 PDF로 다운로드할 수 있는" 서비스의
**MVP PRD를 작성시키기 위한 메타프롬프트**입니다. 아래 프롬프트 전체를 복사해 AI(Claude 등)에게
그대로 입력하면, 정해진 구조와 깊이로 PRD 문서가 산출됩니다.

프로젝트를 새로 정의하거나 범위가 바뀌면 `{{ }}` 로 표시된 변수만 채우고 나머지 지시문은
그대로 유지하세요. 지시문 자체를 수정하면 결과물의 일관성이 깨질 수 있습니다.

---

## 사용 방법

1. 아래 "메타프롬프트 본문"의 `{{변수}}` 부분을 실제 값으로 치환합니다.
2. 전체를 Claude(또는 동급 LLM)에게 그대로 전달합니다.
3. 산출된 PRD는 `docs/PRD.md`에 저장하는 것을 권장합니다.
4. PRD 리뷰 후 요구사항이 바뀌면, 메타프롬프트의 변수만 갱신해 재생성하세요 — 매번 처음부터
   새로 쓰지 않아도 됩니다.

## 메타프롬프트 본문

```
당신은 시니어 프로덕트 매니저입니다. 아래 서비스에 대한 MVP PRD(Product Requirements
Document)를 작성해 주세요. 산출물은 개발팀이 바로 스프린트 계획에 착수할 수 있을 만큼
구체적이어야 하지만, MVP 범위를 벗어나는 기능은 절대 포함하지 마세요.

## 서비스 개요
- 서비스명: {{서비스명, 예: 견적서 웹 뷰어}}
- 한 줄 요약: 노션(Notion)에 입력한 견적서 내용을 클라이언트가 고유 링크로 웹에서
  확인하고, 필요 시 PDF로 다운로드할 수 있는 서비스
- 핵심 사용자: (1) 견적서를 작성하는 내부 담당자(이하 "작성자"),
  (2) 견적서를 열람하는 외부 클라이언트(이하 "클라이언트")
- 데이터 소스: Notion 데이터베이스/페이지 ({{Notion DB 구조 또는 "미정, 제안 요청" 명시}})
- 기술 스택 제약: Next.js {{버전, 예: 16}}, React {{버전, 예: 19}}, Tailwind CSS {{버전}},
  shadcn/ui 컴포넌트 사용. 이 스택과 충돌하는 제안은 하지 말 것.
- 배포/운영 환경: {{예: Vercel, 사내 서버 등 — 미정이면 "미정"으로 표기}}

## 작성 원칙
1. MVP 범위를 명확히 좁히세요. "있으면 좋은 기능"은 반드시 "다음 버전(Out of Scope)"으로
   분리하고, 왜 이번 범위에서 제외했는지 한 줄로 근거를 남기세요.
2. 모든 기능 요구사항은 "사용자가 무엇을 할 수 있는가"를 기준으로 서술하고, 검증 가능한
   완료 조건(Acceptance Criteria)을 함께 제시하세요.
3. Notion을 데이터 소스로 쓸 때 발생하는 제약(레이트리밋, 스키마 변경, 인증 방식, 실시간성
   여부)을 리스크 섹션에서 반드시 짚으세요.
4. 클라이언트가 인증 없이 접근하는 공개 링크 구조이므로, 링크 추측/무단 접근에 대한
   최소한의 보안 고려사항(예: 예측 불가능한 slug, 만료 정책)을 포함하세요.
5. PDF 다운로드는 브라우저에서 보이는 내용과 동일한 결과물을 보장해야 함을 명시하고,
   구현 방식 후보(예: 서버사이드 렌더링 후 변환 vs 클라이언트 print)를 장단점과 함께
   비교하세요. 특정 라이브러리를 단정하지 말고 옵션으로 제시하세요.
6. 확실하지 않은 정보는 추측해서 채우지 말고, "확인 필요"로 표시한 뒤 PRD 하단의
   "확인이 필요한 질문" 섹션에 모아주세요.
7. 문서 전체는 한국어로 작성하고, 코드나 구현 세부사항(파일 경로, 함수명 등)은 이 단계에서
   작성하지 마세요. PRD는 "무엇을·왜"를 다루고, "어떻게"는 별도 기술 설계 문서의 몫입니다.

## 출력 형식 (아래 목차와 순서를 그대로 따를 것)

1. **개요 (Overview)**
   - 배경 및 문제 정의
   - 목표(Goals)와 목표가 아닌 것(Non-Goals)

2. **사용자 정의**
   - 페르소나별 니즈와 사용 맥락 (작성자 / 클라이언트)

3. **핵심 사용자 시나리오 (User Flow)**
   - 작성자: 견적서 작성 → 게시 → 링크 공유
   - 클라이언트: 링크 접속 → 웹에서 견적서 열람 → PDF 다운로드
   - 각 단계별 예외 상황(예: 만료된 링크, Notion 동기화 실패) 포함

4. **기능 요구사항 (Functional Requirements)**
   - 기능별로 번호를 매기고, 우선순위(P0/P1/P2)와 완료 조건을 표로 정리
   - P0는 MVP 출시에 반드시 필요한 것만

5. **비기능 요구사항 (Non-Functional Requirements)**
   - 성능(로딩 속도), 반응형/모바일 대응, 접근성, 브라우저 호환성, 보안

6. **데이터 & 연동 (Notion 연동)**
   - Notion 데이터를 웹 화면 필드로 매핑하는 방식(개념 수준)
   - 동기화 방식과 주기(실시간 API 호출 vs 캐싱)에 대한 옵션 비교

7. **화면 정의 (Screens)**
   - 필요한 화면 목록과 각 화면의 목적, 핵심 구성 요소 (와이어프레임 수준 텍스트 설명)

8. **PDF 다운로드 요구사항**
   - 트리거 방식, 파일명 규칙, 웹 화면과의 동일성 보장 기준

9. **Out of Scope (다음 버전으로 이연)**
   - 항목과 제외 근거

10. **성공 지표 (Success Metrics)**
    - MVP 성공 여부를 판단할 정량 지표 2~4개

11. **리스크 및 오픈 이슈**
    - Notion 연동, 보안, 성능 관점의 리스크와 완화 방안

12. **확인이 필요한 질문**
    - 이해관계자에게 반드시 확인받아야 할 항목 리스트

- 개발팀과 비개발 이해관계자가 함께 읽는 문서이므로 과도한 기술 용어는 풀어서 설명
```
