# PRD — 견적서 웹 뷰어 (Invoice Web) MVP

> 이 문서는 `docs/PRD_PROMPT.md`의 메타프롬프트를 기반으로 작성되었습니다.
> 변수 값: 서비스명 "견적서 웹 뷰어", Next.js 16 / React 19 / Tailwind CSS 4 / shadcn/ui,
> 배포 환경 Vercel(가정), Notion DB 스키마는 확인 필요 상태로 표기했습니다.

---

## 1. 개요 (Overview)

### 배경 및 문제 정의
현재 견적서는 Notion에 작성되지만, 클라이언트에게 전달할 때는 Notion 페이지를 그대로
공유하거나 별도로 문서를 재작성해야 합니다. Notion 공유 링크는 브랜딩이 없고, 클라이언트가
PDF로 보관하기 어려우며, 편집 UI가 그대로 노출되어 전문적이지 않습니다. 견적서 작성자는
Notion에서 입력만 하면, 클라이언트는 깔끔한 전용 웹 페이지에서 내용을 확인하고 PDF로
저장할 수 있어야 합니다.

### 목표 (Goals)
- 작성자가 Notion에 견적서를 입력하면, 별도 코드 작업 없이 클라이언트용 웹 페이지가 생성된다.
- 클라이언트는 전달받은 링크만으로 로그인 없이 견적서를 웹에서 열람할 수 있다.
- 클라이언트는 웹에서 보이는 내용과 동일한 PDF를 다운로드할 수 있다.

### 목표가 아닌 것 (Non-Goals)
- 클라이언트의 견적 승인/서명/코멘트 등 상호작용 기능 (다음 버전)
- 다수 견적서에 대한 클라이언트 대시보드/목록 뷰
- Notion 외 데이터 소스(엑셀, 타 CRM 등) 연동
- 결제/청구 연동

## 2. 사용자 정의

| 페르소나 | 니즈 | 사용 맥락 |
|---|---|---|
| 작성자 (내부 담당자) | Notion에서 하던 방식 그대로 견적서를 입력하고, 결과 링크만 클라이언트에게 보내면 끝나길 원함 | 데스크톱, Notion을 상시 사용 중 |
| 클라이언트 (외부) | 링크 클릭 한 번으로 견적 내용을 빠르게 확인하고, 내부 결재/보관용으로 PDF를 저장하길 원함 | 데스크톱/모바일 브라우저, 이메일이나 메신저로 링크 수신 |

## 3. 핵심 사용자 시나리오 (User Flow)

**작성자**
1. Notion 데이터베이스에 견적서 항목(클라이언트명, 품목, 단가, 수량, 합계, 유효기간 등)을 입력한다.
2. 게시 상태(예: Notion 속성 `상태 = 게시됨`)로 변경하면 웹에서 접근 가능한 고유 링크가 생성된다.
   - 예외: 필수 속성이 비어있는 경우 게시되지 않고 작성자에게 확인 필요 (구현 방식 확인 필요)
3. 생성된 링크를 클라이언트에게 이메일/메신저로 공유한다.

**클라이언트**
1. 전달받은 링크로 접속한다.
2. 웹 페이지에서 견적서 내용을 확인한다.
   - 예외: 링크가 만료되었거나 존재하지 않는 경우 안내 화면 표시
   - 예외: Notion 동기화 실패 시 최신 데이터 대신 오류 또는 마지막 캐시본 안내 (정책 확인 필요)
3. "PDF로 다운로드" 버튼을 눌러 견적서를 PDF로 저장한다.

## 4. 기능 요구사항 (Functional Requirements)

| # | 기능 | 우선순위 | 완료 조건 (Acceptance Criteria) |
|---|---|---|---|
| F1 | Notion 데이터 기반 견적서 웹 페이지 렌더링 | P0 | 지정된 Notion 항목의 클라이언트명·품목·단가·수량·합계·유효기간이 웹 페이지에 정확히 표시된다 |
| F2 | 고유 링크(slug) 발급 | P0 | 게시된 견적서마다 추측 불가능한 고유 URL이 발급되고, 해당 URL로만 접근 가능하다 |
| F3 | 비로그인 공개 열람 | P0 | 클라이언트는 별도 인증 없이 링크만으로 견적서를 열람할 수 있다 |
| F4 | PDF 다운로드 | P0 | 다운로드한 PDF가 웹 화면과 동일한 내용·레이아웃을 유지한다 |
| F5 | 잘못된/만료된 링크 처리 | P0 | 존재하지 않거나 만료된 링크 접속 시 명확한 안내 화면이 표시된다 |
| F6 | 모바일 반응형 열람 | P1 | 모바일 브라우저에서 레이아웃 깨짐 없이 견적서를 확인할 수 있다 |
| F7 | 링크 유효기간 설정 | P1 | 작성자가 지정한 유효기간 이후 링크 접근 시 만료 안내가 표시된다 |
| F8 | 견적서 조회 이력(단순 로그) | P2 | 언제 클라이언트가 열람했는지 작성자가 확인할 수 있다 |

## 5. 비기능 요구사항 (Non-Functional Requirements)

- **성능**: 견적서 페이지 최초 로딩 3초 이내 (일반 브로드밴드 기준)
- **반응형**: 모바일/데스크톱 브라우저 모두 지원, 주요 뷰포트에서 레이아웃 깨짐 없음
- **접근성**: 시맨틱 마크업과 적절한 대비(색 대비 WCAG AA 수준) 준수
- **브라우저 호환성**: 최신 Chrome, Safari, Edge 지원 (IE 미지원)
- **보안**: 링크 slug는 순차 번호가 아닌 예측 불가능한 값 사용, 만료된 견적서는 데이터 노출 없이 접근 차단

## 6. 데이터 & 연동 (Notion 연동)

### 필드 매핑 (개념 수준)
Notion 데이터베이스의 속성을 웹 화면 필드로 매핑합니다. 정확한 속성명과 타입은 **확인 필요**하며,
아래는 예상 매핑입니다.

| Notion 속성 (예상) | 웹 화면 필드 |
|---|---|
| 클라이언트명 | 수신자명 |
| 항목/품목 | 견적 항목 목록 |
| 단가, 수량 | 항목별 금액 계산 |
| 합계 | 총 견적 금액 |
| 유효기간 | 견적 유효기간 표시 및 만료 판단 |
| 상태 | 게시 여부 판단 |

### 동기화 방식 옵션 비교

| 방식 | 장점 | 단점 |
|---|---|---|
| A. 요청 시 Notion API 실시간 조회 | 항상 최신 데이터 반영, 별도 저장소 불필요 | Notion API 레이트리밋에 취약, 응답 지연 가능 |
| B. 게시 시점에 스냅샷 저장 후 서빙 | 응답 속도 빠르고 안정적, 레이트리밋 영향 적음 | Notion 원본 수정 시 재게시 필요, 별도 저장소 필요 |

→ MVP 권장안은 **확인 필요** (트래픽 규모와 데이터 최신성 요구 수준에 따라 결정)

## 7. 화면 정의 (Screens)

| 화면 | 목적 | 핵심 구성 요소 |
|---|---|---|
| 견적서 상세 페이지 | 클라이언트가 견적 내용을 확인하는 메인 화면 | 클라이언트명, 견적 항목 표, 합계, 유효기간, PDF 다운로드 버튼 |
| 링크 오류 페이지 | 잘못되거나 만료된 링크 접근 시 안내 | 오류 메시지, (선택) 문의 연락처 |

작성자용 게시/관리 화면은 Notion 자체를 그대로 사용하므로 별도 화면을 만들지 않습니다.

## 8. PDF 다운로드 요구사항

- **트리거 방식**: 견적서 상세 페이지의 "PDF 다운로드" 버튼 클릭
- **파일명 규칙**: `견적서_{클라이언트명}_{날짜}.pdf` (형식 확인 필요)
- **동일성 보장**: PDF는 웹 화면에 표시된 내용·순서·금액과 100% 일치해야 하며, 여백/폰트 깨짐이 없어야 함
- **구현 방식 후보**
  - 서버사이드 렌더링 후 PDF 변환: 브라우저 환경 차이에 영향받지 않아 결과물이 일관됨, 서버 리소스 필요
  - 클라이언트 브라우저 print-to-PDF 활용: 구현이 간단, 브라우저별 렌더링 차이로 결과물이 달라질 위험
  - → 최종 방식은 **확인 필요** (안정적 동일성이 중요하다면 서버사이드 렌더링 권장)

## 9. Out of Scope (다음 버전으로 이연)

| 항목 | 제외 근거 |
|---|---|
| 클라이언트 승인/서명 기능 | MVP는 "열람+다운로드"까지만 검증하는 것이 목표이며, 승인 플로우는 별도 워크플로우 설계가 필요 |
| 견적서 목록/대시보드 | 클라이언트는 개별 링크로만 접근하는 것으로 충분, 목록 UI는 계정 체계를 전제로 함 |
| Notion 외 데이터 소스 연동 | 현재 팀의 실제 작업 도구가 Notion이므로 다른 소스는 검증되지 않은 요구 |
| 조회 이력 상세 분석 | 단순 로그(F8, P2) 이상의 분석 기능은 초기 검증 단계에서 우선순위가 낮음 |

## 10. 성공 지표 (Success Metrics)

- 견적서 게시 후 클라이언트 열람까지 걸리는 평균 시간 (링크 공유 프로세스가 실제로 빨라졌는지 측정)
- 견적서 페이지 열람 대비 PDF 다운로드 전환율
- 링크 접속 실패(오류 페이지 노출) 비율 1% 미만 유지
- 작성자 설문 기준 "Notion 입력만으로 충분했다" 응답 비율

## 11. 리스크 및 오픈 이슈

- **Notion API 레이트리밋**: 실시간 조회 방식(옵션 A) 채택 시 다수 클라이언트가 동시 접속하면
  API 제한에 걸릴 수 있음 → 캐싱 또는 스냅샷 방식(옵션 B) 검토 필요
- **Notion 스키마 변경 취약성**: 담당자가 Notion 속성명을 임의로 바꾸면 매핑이 깨질 수 있음
  → 속성명 검증 또는 속성 ID 기반 매핑 필요
- **인증 방식**: Notion Integration Token 관리 방식(서버 환경변수 등) 확정 필요
- **공개 링크 보안**: slug 예측 가능성, 만료 정책 미비 시 무단 열람 위험 → F2, F7과 연계해 정책 확정 필요
- **PDF 렌더링 일관성**: 구현 방식(8번 섹션)에 따라 브라우저 간 결과물이 달라질 수 있음

## 12. 확인이 필요한 질문

1. Notion 데이터베이스의 실제 속성명·타입 구조는 무엇인가?
2. 견적서 "게시" 상태를 어떤 방식으로 트리거할 것인가? (Notion 속성 변경만으로 충분한가, 별도 자동화가 필요한가)
3. 데이터 동기화는 실시간 조회(A)와 스냅샷(B) 중 무엇을 선택할 것인가?
4. 링크 유효기간의 기본값과 만료 후 데이터 처리 정책(완전 차단 vs 안내만)은?
5. PDF 파일명 규칙과 구현 방식(서버사이드 vs 클라이언트 print)은 무엇으로 확정할 것인가?
6. 배포 환경이 Vercel로 확정되었는가, 아니면 별도 인프라를 사용하는가?
7. 조회 이력(F8)이 필요한 최소 정보는 무엇인가? (일시만인지, IP/기기 정보까지 필요한지)
